# TG-332 (AAPM, 2025): como validar sistemas "caixa-preta" do fornecedor

**Em uma frase.** Dá ao físico um método para aceitar e manter sob QA sistemas do fornecedor cujo funcionamento interno não é visível (**MPC do TrueBeam**, dados de feixe pré-configurados, dosimetria portal do Halcyon, autocontorno e outros modelos de IA), distinguindo **ferramenta de QA** de **ferramenta de serviço** e avaliando a **independência** de quem a desenvolveu [TG-332 p. 1, 4–6].

PDF de cerca de 20 páginas, texto limpo.

## Conceitos

| Conceito | Definição | Página |
| --- | --- | --- |
| Caixa-preta | Entrada, algoritmo e saída não acessíveis ao usuário (só passa/falha e tendência). Ex.: **MPC** | Tab. 1 [TG-332 p. 4] |
| Caixa-cinza | Sabe-se o bastante para reproduzir com medida ou ferramenta de terceiros. Ex.: análise de log no Mobius | [TG-332 p. 4] |
| Caixa-branca | Algoritmo aberto. Ex.: planura e simetria do software do tanque | [TG-332 p. 4] |
| **Ferramenta de QA** | Feita para o usuário; o fornecedor deve documentar, treinar, avisar defeitos e mudanças por *release note* | [TG-332 p. 4–5] |
| **Ferramenta de serviço** | Feita para o engenheiro do fornecedor (ex.: **MPC no TrueBeam**); usar no QA clínico é **por conta e risco do físico**, que deve fazer validação independente antes | [TG-332 p. 4–5] |
| Independência (IEEE) | Técnica, gerencial e financeira. As três = IV&V clássica (aceitável até para calibração e débito); faltando uma = IV&V modificada (só risco baixo a médio sem validação extra) | [TG-332 p. 5–6] |

## Recomendações (seção 6) [TG-332 p. 11–12]

1. Validar com **testes fim a fim no uso clínico pretendido**, inclusive perto dos limites; não usar fora dos casos testados.
2. **Introduzir desvio conhecido** (offset) e ver se o sistema detecta.
3. Comparar testes entre si; **acompanhar métricas com controle estatístico** (tolerância e ação); acompanhar incidentes.
4. Análise de risco para focar nos parâmetros de maior risco; coletar dados independentes quando preciso; usar dados agregados de outros usuários e a literatura.
5. **Procedimento escrito para upgrade** do sistema caixa-preta, com casos fim a fim para repetir depois.
6. Perguntar ao fornecedor o nível de independência no desenvolvimento.
7. Dados de referência do fornecedor (ex.: dados de feixe do Eclipse) são aceitáveis no comissionamento **desde que o modelo seja validado** pela orientação da AAPM.

## MPC do TrueBeam (Apêndice A3) [TG-332 p. 16–17]

- No TrueBeam é **ferramenta de serviço**, complementar; **não substitui** o QA do físico (no Halcyon é obrigatório antes do uso diário).
- Validar de forma independente o que pesa na segurança: **débito** (câmara e fantoma), **uniformidade** (arranjo ou filme), **MLC** (picket fence), **isocentro** (Winston-Lutz com gantry e mesa) e **deslocamento de mesa por imagem** (alvo oculto).
- Acompanhar o MPC lado a lado com os testes independentes por **3 meses ou mais** antes de usá-lo para substituir qualquer teste diário ou mensal.

## Como se aplica no CLINICA

- A07/A13 (CEL, TrueBeam 4045; DUO, VitalBeam 4199): se o MPC for usado no CQ diário, registrar a validação de 3 meses contra câmara, picket fence e Winston-Lutz, e o procedimento de revalidação após upgrade.
- B01: os dados "representativos" do Eclipse usados em algum feixe precisam de validação do modelo (MPPG-5b).
- B10: o mesmo roteiro vale para ferramentas de terceiros e para o pylinac (caixa-branca, mas validar entrada e saída).
